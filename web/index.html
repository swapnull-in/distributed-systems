Write skew under snapshot isolation

Two transactions read the same snapshot, each writes a different row, and no write-write conflict exists — so Snapshot Isolation (Postgres REPEATABLE READ) lets both commit and together they break an invariant that spans the rows.

Two on-call doctors

Invariant: at least one doctor on call. Both start on call; each transaction wants to go off.

The proof: under SI both read "2 on call" from the same snapshot and each writes a different row — no conflict to detect, so both commit → 0 on call. Any "exactly one of N" or "no overlap" invariant is a write-skew risk. The fix makes the conflict materialize: SERIALIZABLE (SSI aborts one, expect 40001 retries) or lock the rows both depend on so the second re-reads and refuses.

CAP — what a partition actually forces

P isn't optional on a real network. During a partition you choose, per data path: keep Consistency (minority refuses writes) or Availability (both sides accept and diverge). Move node 2 across the cut, pick a posture, and write from each side.

5 nodes, quorum = 3

Click node 2 to move it across the cut; sides {0,1,2} vs {3,4} by default.

Pick a posture and a side, then write.

The proof: CP makes the minority side refuse writes (no quorum) so there's one truth — availability sacrificed. AP lets both sides accept, so two versions live at once and you pay the bill at reconciliation (LWW / vectors / CRDT). Lead with PACELC: even with no partition, the latency-vs-consistency trade (waiting for a quorum ack) is paid on every request.

Session guarantees — read-your-writes

Under async replication you can write to the primary and then read a lagging replica that hasn't caught up — "I just posted it, where is it?". A per-session LSN token fixes ~90% of these without paying for full linearizability.

The proof: naive, your read hits the lagging replica and your own write is missing until it replicates. Read-your-writes carries the write's LSN as a session token and routes the read only to a node caught up past it — cheap, sticky, per-session. (The other guarantees: monotonic reads, monotonic writes, writes-follow-reads.)

Quorum reads — R + W > N and read-repair

Leaderless replication: write to W of N, read from R. If R + W > N the read and write sets must overlap, so a read always sees the latest write; a stale replica is healed by read-repair on the read path.

W · write replicas2
R · read replicas2
R+W = 4 > N=3 ✓ overlap
Write v2, then read — try R+W>N vs R+W≤N.

The proof: writes land on the first W replicas, reads on the last R. Those sets overlap exactly when W + R > N (pigeonhole) — so a quorum read always includes a replica with the latest version, and read-repair writes it back to the stale ones. Set R+W ≤ N and the read can miss the write: fast, but stale. Sloppy quorum + hinted handoff trade this for availability under partition.

Fencing tokens — a lock alone isn't safe

A lock holder can be paused (stop-the-world GC, hypervisor stall) past its lease and wake up still believing it holds the lock. A lock can never fix this — safety comes from the resource rejecting any write whose fencing token is below the highest it has seen.

The proof: without fencing, paused A wakes and clobbers B's write — silent corruption. With a monotonic token, A writes with its old token and the resource rejects it (token 1 < 2). Safety lives at the resource, not the lock. YAGNI: a plain lock is fine for deduping a cron job; fencing is for correctness-critical paths (money, uniqueness).

Distributed transactions — 2PC vs Saga

A transaction across services with no shared memory. 2PC is atomic but if the coordinator dies after PREPARE, participants hang in-doubt with locks held. A Saga is local transactions with compensations — no global lock, and a late failure unwinds cleanly.

Pick a protocol and run it.

The proof: kill the 2PC coordinator after PREPARE and both participants are in-doubt — locks held indefinitely, blocking every other txn on those rows. The same flow as a Saga runs local commits and, on a late failure, compensates in reverse (release, refund) with no global lock ever held. Default to Saga; flip to 2PC only for a single tightly-coupled stack needing true atomicity.

Dual-write vs the transactional outbox

A service must change its DB and publish an event. Doing them as two separate steps means a crash between can leave them disagreeing. The outbox writes the event into the DB in the same transaction; a relay publishes it at-least-once; consumers dedupe by idempotency key.

The proof: dual-write commits the DB then 💥 crashes before publishing → order PAID but no event, permanently inconsistent. The outbox commits the state change and the event row atomically, so a crash just delays delivery — the relay replays the outbox (at-least-once). A duplicate delivery is deduped by idempotency key → effectively-once. There is no exactly-once on the wire.

Retry storm → metastable failure

A brief capacity dip (rounds 3–5). Watch what happens after capacity recovers: naive retries become the load and the system stays collapsed — a stable-but-broken equilibrium — until a retry budget and circuit breaker break the loop.

The proof: naive retries turn a 3-round dip into a permanent outage — retries become the load, so even after capacity returns the useful work stays near zero. A retry budget caps the amplification and the breaker sheds load so the dependency can recover.

Bulkheads & shuffle sharding — blast radius

One poisoned tenant that ties up whatever workers it lands on shouldn't take everyone down. Bulkheads give each tenant its own pool; shuffle sharding gives each a random small subset of workers, so any two tenants collide combinatorially rarely.

Poison one tenant under each scheme and watch the blast radius.
—tenants affected (blast radius)

The proof: a shared pool means one poison tenant saturates every worker → 100% blast radius. Bulkheads dedicate a pool per tenant → only that tenant suffers (rigid, wastes capacity). Shuffle sharding gives each tenant a random k-of-n shard; a victim is only sunk if its whole shard sits inside the poison's — probability 1 / C(n,k) ≈ 0.8% here — so the blast radius drops to a few percent without a full pool each. This is the AWS Route 53 / cell-based trick.

Clocks — order without a shared now

A lower wall-clock timestamp does not mean "happened first" — skew and NTP steps corrupt ordering. Watch wall-clock LWW pick the wrong winner, Lamport restore the order, and vector clocks flag a truly concurrent pair instead of silently merging it.

Hybrid Logical Clock — the pragmatic default

HLC wraps Lamport's causal guarantee around physical time: a timestamp (pt, l) where pt tracks the wall clock and a tiny counter l breaks ties. You get "if a→b then ts(a) < ts(b)" and near-real timestamps, in constant size, with no atomic clocks.

Multi-region — the fiber-cut drill

Three regions at the same steady utilization. Cut one — the survivors must absorb its load with capacity that already exists (autoscaling can't save you: cold-start stampede on the cloud's worst day).

steady utilization66%
Set a utilization, then cut a region.

The proof: with 3 regions each must run at ≤ 66% so a survivor peaks at ≤ 100% (each takes 1.5× its load). That "idle" third isn't waste — it's the RTO insurance premium. Cut it to save money and the next region loss becomes an outage.
